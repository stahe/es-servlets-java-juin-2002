    6. XML y Java

    En este capítulo, presentamos el uso de documentos XML con Java. Lo haremos en el contexto de la aplicación fiscal estudiada en el capítulo anterior.

    6.1. Archivos XML y hojas de estilo XSL

    Consideremos el siguiente archivo XML, simulations.xml, que podría representar los resultados de simulaciones de cálculo de impuestos:

    <?xml version="1.0" encoding="ISO-8859-1"?>
<simulations>
  <simulation marie="oui" enfants="2" salaire="200000" impot="22504"/>
  <simulation marie="non" enfants="2" salaire="200000" impot="33388"/>
</simulations>

    Al visualizarlo con IE 6, se obtiene el siguiente resultado:

    IE6 reconoce que se trata de un archivo XML (gracias a la extensión .xml del archivo) y lo formatea a su manera. Con Netscape, se obtiene una página en blanco. Sin embargo, si se consulta el código fuente (Ver/Fuente), se puede ver el archivo XML original:

    ¿Por qué Netscape no muestra nada? Porque necesita una hoja de estilo que le indique cómo transformar el archivo XML en un archivo HTML que luego pueda mostrar. Resulta que IE 6 tiene una hoja de estilo predeterminada cuando el archivo XML no proporciona una, que era el caso aquí.

    Existe un lenguaje llamado XSL (eXtended StyleSheet Language) que permite describir las transformaciones necesarias para convertir un archivo XML en cualquier archivo de texto. XSL admite numerosas instrucciones y se asemeja mucho a los lenguajes de programación. No entraremos en detalles aquí, ya que eso requeriría docenas de páginas. Nos limitaremos a describir dos ejemplos de hojas de estilo XSL. El primero es el que transformará el archivo XML simulations.xml en código HTML. Modificamos este último para que especifique la hoja de estilo que los navegadores pueden utilizar para transformarlo en un documento HTML, que luego pueden mostrar:

    <?xml version="1.0" encoding="ISO-8859-1" ?>
<?xml-stylesheet type="text/xsl" href="simulations.xsl"?>
<simulations>
  <simulation marie="oui" enfants="2" salaire="200000" impot="22504"/>
  <simulation marie="non" enfants="2" salaire="200000" impot="33388"/>
</simulations>

    El comando XML

    <?xml-stylesheet type="text/xsl" href="simulations.xsl"?>

    designa el archivo simulations.xsl como una hoja de estilo XML de tipo text/xsl, es decir, un archivo de texto que contiene código XSL. Los navegadores utilizarán esta hoja de estilo para transformar el texto XML en un documento HTML. Este es el resultado obtenido con Netscape 7 al cargar el archivo XML simulations.xml:

    Cuando vemos el código fuente del documento (Ver/Fuente), vemos el documento XML original en lugar del documento HTML mostrado:

                          <xsl:apply-templates select="/simulations/simulation"/>
                        </table>

     </html>
        </xsl:template>


    <xsl:template match="simulation">
          <tr>
            <td><xsl:value-of select="@marie"/></td>
            <td><xsl:value-of select="@enfants"/></td>
            <td><xsl:value-of select="@salaire"/></td>
            <td><xsl:value-of select="@impot"/></td>
        </tr>
       </xsl:template>
  </xsl:stylesheet>
    • Una hoja de estilo XSL es un archivo XML y, por lo tanto, sigue las reglas de XML. Entre otras cosas, debe estar «bien formada», lo que significa que todas las etiquetas de apertura deben cerrarse.
    • El archivo comienza con dos directivas XML que pueden incluirse en cualquier hoja de estilo XSL: 
    <?xml version="1.0" encoding="ISO-8859-1"?>
  <xsl:stylesheet version="1.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">

    El atributo encoding="ISO-8859-1" permite utilizar caracteres acentuados en la hoja de estilo.

    • La etiqueta <xsl:output method="html" indent="yes"/> indica al intérprete XSL que se desea generar código HTML «sangrado».
    • La etiqueta <xsl:template match="element"> se utiliza para definir el elemento del documento XML al que se aplicarán las instrucciones que se encuentran entre <xsl:template ...> y </xsl:template>. 
        <xsl:template match="/">
................
        </xsl:template>

    En el ejemplo anterior, el elemento «/» denota la raíz del documento. Esto significa que, tan pronto como se encuentre el inicio del documento XML, se ejecutarán los comandos XSL situados entre las dos etiquetas.

    • Todo lo que no sea una etiqueta XSL se incluye tal cual en el flujo de salida. Las propias etiquetas XSL se ejecutan. Algunas de ellas producen un resultado que se incluye en el flujo de salida. Examinemos el siguiente ejemplo: 
        <xsl:template match="/">
        <html>
          <head>
            <title>Simulations de calculs d'impôts</title>
        </head>
          <body>
            <center>
              <h3>Simulations de calculs d'impôts</h3>
            <hr/>
            <table border="1">
                    <th>marié</th><th>enfants</th><th>salaire</th><th>impôt</th>
                          <xsl:apply-templates select="/simulations/simulation"/>
                        </table>
          </center>
        </body>
      </html>
        </xsl:template>

    Tenga en cuenta que el documento XML que se está analizando es el siguiente:

    <?xml version="1.0" encoding="ISO-8859-1"?>
<simulations>
  <simulation marie="oui" enfants="2" salaire="200000" impot="22504"/>
  <simulation marie="non" enfants="2" salaire="200000" impot="33388"/>
</simulations>

    Desde el inicio del documento XML analizado (match="/"), el procesador XSL generará el texto

    <html>
          <head>
            <title>Simulations de calculs d'impôts</title>
        </head>
          <body>
            <center>
              <h3>Simulations de calculs d'impôts</h3>
            <hr>
            <table border="1">
                    <th>marié</th><th>enfants</th><th>salaire</th><th>impôt</th>

    Ten en cuenta que en el texto original teníamos <hr/> y no <hr>. En el texto original no podíamos escribir <hr>, ya que, aunque es una etiqueta HTML válida, no lo es en XML. Sin embargo, en este caso estamos trabajando con texto XML que debe estar «bien formado», lo que significa que todas las etiquetas deben cerrarse. Por lo tanto, escribimos <hr/>, y como hemos escrito <xsl:output text="html ...> el procesador XSL transformará el texto <hr/> en <hr>. A continuación de este texto aparecerá el texto generado por el comando XSL:

          <xsl:apply-templates select="/simulations/simulation"/>

    Más adelante veremos qué es este texto. Por último, el intérprete añadirá el texto:

                        </table>
          </center>
        </body>
      </html>

    La directiva <xsl:apply-templates select="/simulations/simulation"/> indica al procesador XSL que aplique la «plantilla» al elemento /simulations/simulation. Se ejecutará cada vez que el intérprete XSL encuentre una etiqueta <simulation>..</simulations> o <simulation/> dentro de una etiqueta <simulations>..</simulations> en el texto XML analizado. Al encontrar la etiqueta <simulation>, el intérprete ejecutará las instrucciones de la siguiente plantilla:

        <xsl:template match="simulation">
          <tr>
            <td><xsl:value-of select="@marie"/></td>
            <td><xsl:value-of select="@enfants"/></td>
            <td><xsl:value-of select="@salaire"/></td>
            <td><xsl:value-of select="@impot"/></td>
        </tr>
       </xsl:template>

    Considere las siguientes líneas XML:

    <simulations>
  <simulation marie="oui" enfants="2" salaire="200000" impot="22504"/>

    La línea <simulation ..> corresponde a la plantilla para la instrucción XSL <xsl:apply-templates select="/simulations/simulation">. Por lo tanto, el intérprete XSL intentará aplicar las instrucciones que coincidan con esta plantilla. Encontrará la plantilla <xsl:template match="simulation"> y la ejecutará. Recordemos que todo lo que no sea un comando XSL pasa sin cambios por el intérprete XSL, mientras que los comandos XSL se sustituyen por el resultado de su ejecución. La instrucción XSL <xsl:value-of select="@champ"/> se sustituye así por el valor del atributo «champ» del nodo analizado (en este caso, un nodo <simulation>). El análisis de la línea XML anterior producirá el siguiente resultado:

    6.2. Aplicación de cálculo de impuestos: versión 6

    6.2.1. Los archivos XML y las hojas de estilo XSL de la aplicación de cálculo de impuestos

    Volvamos a la aplicación web de impuestos y modifiquémosla para que la respuesta enviada a los clientes esté en formato XML en lugar de HTML. Esta respuesta XML irá acompañada de una hoja de estilo XSL para que los navegadores puedan mostrarla. En la sección anterior, presentamos:

    • el archivo simulations.xml, que es un prototipo de respuesta XML que contiene simulaciones de cálculo de impuestos
    • el archivo simulations.xsl, que será la hoja de estilo XSL que acompañará a esta respuesta XML

    También debemos tener en cuenta el caso de una respuesta que contenga errores. El prototipo de la respuesta XML en este caso será el siguiente archivo errors.xml:

    <?xml version="1.0" encoding="windows-1252"?>
<?xml-stylesheet type="text/xsl" href="erreurs.xsl"?>
<erreurs>
    <erreur>erreur 1</erreur>
  <erreur>erreur 2</erreur>
</erreurs>

    La hoja de estilo errors.xsl utilizada para mostrar este documento XML en un navegador será la siguiente:

    <?xml version="1.0" encoding="windows-1252"?>
  <xsl:stylesheet version="1.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
      <xsl:output method="html" indent="yes"/>

    <xsl:template match="/">
        <html>
          <head>
            <title>Simulations de calculs d'impôts</title>
        </head>
          <body>
            <center>
              <h3>Simulations de calculs d'impôts</h3>
          </center>            
          <hr/>
          Les erreurs suivantes se sont produites :
          <ul>
                  <xsl:apply-templates select="/erreurs/erreur"/>
              </ul>            
        </body>
      </html>
        </xsl:template>

    <xsl:template match="erreur">
          <li><xsl:value-of select="."/></li>
        </xsl:template>
</xsl:stylesheet>

    Esta hoja de estilo introduce un comando XSL que aún no hemos visto: <xsl:value-of select="."/>. Este comando devuelve el valor del nodo analizado, en este caso un nodo <error>text</error>. El valor de este nodo es el texto que se encuentra entre las etiquetas de apertura y cierre, en este caso «text».

    El código errors.xml es transformado por la hoja de estilo errors.xsl en el siguiente documento HTML:

    <html>
<head>
<title>Simulations de calculs d'impots</title>
</head>
<body>
<center>
<h3>Simulations de calculs d'impots</h3>
</center>
<hr>
          Les erreurs suivantes se sont produites :
<ul>
<li>erreur 1</li>
<li>erreur 2</li>
</ul>
</body>
</html>

    • El servlet se llama xmlsimulations y se basa en el archivo xmlsimulations.class.
    • Sus parámetros son DSNimpots, admimpots y mdpimpots, que son necesarios para acceder a la base de datos fiscal. Además, acepta otros dos parámetros:
      • xslSimulations, que es el nombre del archivo de hoja de estilo que debe acompañar a la respuesta XML que contiene las simulaciones
      • xslErrors, que es el nombre de la hoja de estilo que debe acompañar a la respuesta XML que contenga cualquier error
    • Tiene un alias, xmlsimulations, que permite acceder a él a través de la URL http://localhost:8080/impots/xmlsimulations.

    El esqueleto del servlet xmlsimulations es similar al del servlet simulations ya comentado. La principal diferencia es que debe generar XML en lugar de HTML. Esto supondrá la eliminación de los archivos JSP utilizados en aplicaciones anteriores. Su función principal era mejorar la legibilidad del código HTML generado, evitando que quedara oculto dentro del código Java del servlet. Esta función ya no es necesaria. El servlet tiene dos tipos de código XML que generar:

    • uno para las simulaciones
    • otro para los errores

    Anteriormente presentamos y examinamos los dos tipos de respuestas XML que deben proporcionarse en estos dos casos, así como las hojas de estilo que deben acompañarlas. El código del servlet es el siguiente:

    import java.io.*;
import javax.servlet.*;
import javax.servlet.http.*;
import java.util.regex.*;
import java.util.*;

public class xmlsimulations extends HttpServlet{

    // instance variables
    String msgErreur=null;
    String xslSimulations=null;
    String xslErreurs=null;
    String DSNimpots=null;
    String admimpots=null;
    String mdpimpots=null;
    impotsJDBC impots=null;

    //-------- GET
    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException{

        // retrieve the write stream to the client
        PrintWriter out=response.getWriter();

        // specify the type of response
        response.setContentType("text/xml");

         // error list
        ArrayList erreurs=new ArrayList();

         // was the initialization successful?
        if(msgErreur!=null){
             // that's it - we send the response with errors to the server
            erreurs.add(msgErreur);
            sendErreurs(out,xslErreurs,erreurs);
             // it's over
            return;
        }

         // retrieve previous simulations from the session
        HttpSession session=request.getSession();
        ArrayList simulations=(ArrayList)session.getAttribute("simulations");
        if(simulations==null) simulations=new ArrayList();

        // retrieve the parameters of the current query
        String optMarie=request.getParameter("optMarie");              // marital status
        String txtEnfants=request.getParameter("txtEnfants");       // no. of children
        String txtSalaire=request.getParameter("txtSalaire");       // annual salary

         // do we have all the expected parameters
        if(optMarie==null || txtEnfants==null || txtSalaire==null){
             // missing parameters
             // send response with errors
            erreurs.add("Demande incomplète. Il manque des paramètres");
            sendErreurs(out,xslErreurs,erreurs);
             // it's over
            return;
        }

         // we have all the parameters - we check them
         // marital status
        if( ! optMarie.equals("oui") && ! optMarie.equals("non")){
             // error
            erreurs.add("Etat marital incorrect");
        }
         // number of children
        txtEnfants=txtEnfants.trim();
        if(! Pattern.matches("^\\d+$",txtEnfants)){
            // error
            erreurs.add("Nombre d'enfants incorrect");
        }
         // salary
        txtSalaire=txtSalaire.trim();
        if(! Pattern.matches("^\\d+$",txtSalaire)){
            // error
            erreurs.add("Salaire incorrect");
        }

        if(erreurs.size()!=0){
            // if there are errors, we report them
            sendErreurs(out,xslErreurs,erreurs);
        }else{
             // no errors
            try{
                 // you can calculate the tax payable
                int nbEnfants=Integer.parseInt(txtEnfants);
                int salaire=Integer.parseInt(txtSalaire);
                String txtImpots=""+impots.calculer(optMarie.equals("oui"),nbEnfants,salaire);
                 // the current result is added to the previous simulations
                String[] simulation={optMarie.equals("oui") ? "oui" : "non",txtEnfants, txtSalaire, txtImpots};
                simulations.add(simulation);
                 // we send the answer with simulations
                sendSimulations(out,xslSimulations,simulations);
            }catch(Exception ex){}
        }//if-else
         // we put the list of simulations back into the session
        session.setAttribute("simulations",simulations);
    }//GET

     //-------- POST
    public void doPost(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException{
        doGet(request,response);
    }//POST

     //-------- INIT
    public void init(){
         // retrieve initialization parameters

    Para analizar un documento XML, nuestra aplicación necesita un analizador de código XML.

                XMLReader parser = XMLReaderFactory.createXMLReader("org.apache.xerces.parsers.SAXParser");

    El analizador XML utilizado es el que proporciona el paquete xerces.jar. El objeto devuelto es de tipo XMLReader. XMLReader es una interfaz, y aquí utilizamos dos de sus métodos:

    void setContentHandler(ContentHandler handler)
    indica al analizador qué objeto ContentHandler gestionará los eventos que genere mientras analiza el documento XML
    void parse(InputSource input)
    inicia el análisis del documento XML pasado como parámetro

    Cuando el analizador analiza el documento XML, emite eventos tales como: «He encontrado el inicio del documento, el inicio de una etiqueta, un atributo de etiqueta, el contenido de una etiqueta, el final de una etiqueta, el final del documento, ...». Pasa estos eventos al objeto ContentHandler que se le ha proporcionado. ContentHandler es una interfaz que define los métodos que deben implementarse para gestionar todos los eventos que el analizador XML puede generar. DefaultHandler es una clase que proporciona una implementación predeterminada de estos métodos. Los métodos implementados en DefaultHandler no hacen nada, pero existen. Cuando necesitamos indicar al analizador qué objeto gestionará los eventos que genera utilizando la instrucción 

    void setContentHandler(ContentHandler handler)

    , resulta conveniente pasar un objeto de tipo DefaultHandler como parámetro. Si nos detuviéramos ahí, no se gestionarían los eventos del analizador, pero nuestro programa sería sintácticamente correcto. En la práctica, pasamos al analizador como parámetro un objeto derivado de la clase DefaultHandler, en el que se redefinen los métodos que gestionan únicamente los eventos que nos interesan. Esto es lo que se hace aquí:

                 // we indicate to the parser the object that will implement the methods
             // startDocument, endDocument, startElement, endElement, characters
            MySaxParser MySaxParserInstance = new MySaxParser();
            parser.setContentHandler(MySaxParserInstance);
             // we indicate to the parser the XML document to be analyzed
            parser.parse(uri);

    Pasamos al analizador una instancia de la clase mySaxParser, que es nuestra clase y que se definió anteriormente mediante la declaración

    public class MySaxParser extends DefaultHandler {

    y comenzamos a analizar el documento cuyo URI se ha pasado como parámetro. A partir de ahí, comienza el análisis del documento XML. El analizador emite eventos y, para cada uno de ellos, llama a un método específico del objeto responsable de gestionar estos eventos; en este caso, nuestro objeto MySaxParser. Este objeto gestiona cinco eventos específicos; los demás se ignoran:

    evento emitido por el analizador
    método de gestión
    inicio del documento
    void startDocument()
    fin del documento
    void finDocumento()
    Inicio de un elemento: <tag>
    public void startElement(String uri, String localName, String qName, Attributes attributes)
    uri: ?
    localName: nombre del elemento analizado. Si el elemento encontrado es <simulations>, localName será «simulations».
    qName: nombre calificado por el espacio de nombres del elemento analizado. Un documento XML puede definir un espacio de nombres, como XX. El nombre calificado de la etiqueta anterior sería entonces XX:simulations.
    attributes: lista de los atributos de la etiqueta
    valor de un elemento:
<tag>valor</tag>
    public void characters(char[] ch, int start, int length)
    ch: matriz de caracteres
    start: índice del primer carácter a utilizar en la matriz ch
    longitud: número de caracteres que se tomarán de la matriz ch
    El método characters se puede llamar repetidamente. Para construir el valor de un elemento, utilizamos un búfer que:
    • inicialmente está vacío
    • llenamos con cada nueva llamada al método characters
    • terminamos al final del elemento 
    Fin de un elemento: </tag> o <tag .../>
    void endElement(String uri, String localName, String qName)
    Los parámetros son los mismos que los del método startElement.

    El método startElement permite recuperar los atributos del elemento utilizando el parámetro attributes de tipo Attributes:

    • El número de atributos está disponible en attributes.getLength()
    • El nombre del atributo i está disponible en attributes.getLocalName(i)
    • El valor del atributo i está disponible en attributes.getValue(i)
    • El valor del atributo localName está disponible en attributes.getValue(localName)

    Una vez explicado esto, el programa anterior y sus ejemplos de ejecución se explican por sí mismos. Se utilizó una expresión regular para recuperar los valores de los elementos, de modo que un texto XML como:

    <erreur>
    erreur 1
</erreur>

    devuelve el texto «error 1» como valor asociado a la etiqueta <error>, sin los espacios ni los saltos de línea que puedan precederla o seguirla.

import org.xml.sax.*;
import org.xml.sax.helpers.*;

import java.io.*;

// the class
public class ImpotsSaxParser extends DefaultHandler {

    // value of a tree element XML
    private StringBuffer valeur=new StringBuffer();
    // a regular expression of an element's value when you want to ignore
     // the "blanks" that precede or follow it
    private Pattern ptnValeur=null;
    private Matcher résultats=null;
     // lists of XML elements
    private ArrayList listeSimulations=new ArrayList();
    private ArrayList listeErreurs=new ArrayList();
     // elements XML
    private ArrayList éléments=new ArrayList();
    String élément="";

     // -------- manufacturer
    public ImpotsSaxParser(BufferedReader IN) throws Exception{
        // creation of a XML analyzer (parser)
        XMLReader parser = XMLReaderFactory.createXMLReader("org.apache.xerces.parsers.SAXParser");
         // we indicate to the parser the object that will implement the methods
         // startDocument, endDocument, startElement, endElement, characters
        parser.setContentHandler(this);
        // initialize an element's value model
        ptnValeur=Pattern.compile("^\\s*(.*?)\\s*$");
         // initially no current XML element
        éléments.add("");
         // document analysis
        parser.parse(new InputSource(IN));
    }//manufacturer

     // -------- startElement
    public void startElement(String uri, String localName, String qName,
        Attributes attributes) throws SAXException {
         // procedure called by the parser when it encounters the start of a tag
         // uri: URI of the analyzed document?
         // localName: name of element being analyzed
         // qName: ditto, but "qualified" by a namespace if there is one
         // attributes: list of element attributes

         // note the name of the element
        élément=localName.toLowerCase();
        éléments.add(élément);
         // does the element have attributes?
        if(élément.equals("simulation") && attributes.getLength()==4){

                                         attributes.getValue("enfants")+","+
                                         attributes.getValue("salaire")+","+
                                         attributes.getValue("impot");
             // add the simulation to the list of simulations
            listeSimulations.add(simulation);
        }//if
    }//startElement

    // -------- characters
    public void characters(char[] ch, int start, int length) throws SAXException {
        // procedure called repeatedly by the parser when it encounters text
         // between two <tag>text</tag> tags

         // the text is added to the value buffer if it is the error element
        if (élément.equals("erreur"))

    public void endElement(String uri, String localName, String qName)
            throws SAXException {
         // procedure called by the parser when it encounters an end of tag
         // uri: URI of the analyzed document?
         // localName: name of element being analyzed
         // qName: ditto, but "qualified" by a namespace if there is one

         // case of error
        if(élément.equals("erreur")){
             // retrieve the value of the error element
            String strValeur=valeur.toString();
             // we strip it of its useless "blanks" and register it in the
             // errors if non-empty
            résultats=ptnValeur.matcher(strValeur);
            if (résultats.find() && ! résultats.group(1).equals("")){
                listeErreurs.add(résultats.group(1));
            }//if
        }
         // set element value to empty
        valeur.setLength(0);
         // reset element name
        éléments.remove(éléments.size()-1);
        élément=(String)éléments.get(éléments.size()-1);
    }//endElement

     // --------- getErreurs
    public ArrayList getErreurs(){
        return listeErreurs;
    }

     // --------- getSimulations
    public ArrayList getSimulations(){
        return listeSimulations;
    }

}//class
    • El constructor recibe el flujo XML IN que se va a analizar y realiza inmediatamente dicho análisis. Una vez completado, el objeto se ha construido y se han creado las listas (ArrayList) de errores (errorList) y simulaciones (simulationList). Lo único que queda por hacer en el procedimiento que ha construido el objeto es recuperar las dos listas utilizando los métodos getErrors y getSimulations.
    • Solo tres eventos generados por el analizador XML son de interés aquí:
      • el inicio de un elemento XML, un evento que será gestionado por el procedimiento startElement. Este procedimiento gestionará las etiquetas <simulation marie=".." enfants=".." salaire=".." impot=".."> y <erreur>...</erreur>.
      • El valor de un elemento XML, un evento que será gestionado por el procedimiento characters.
      • El final de un elemento XML, un evento que será gestionado por el procedimiento endElement.
    • En el procedimiento startElement, si se trata del elemento <simulation marie=".." enfants=".." salaire=".." impot="..">, recuperamos los cuatro atributos utilizando attributes.getValue("nombre del atributo"). En todos los casos, almacenamos el nombre del elemento en una variable element y lo añadimos a una lista (ArrayList) de elementos: elem1, elem2, ..., elemN. Esta lista se gestiona como una pila, donde el último elemento es el elemento XML que se está analizando actualmente. Cuando se produce el evento «fin de elemento», se elimina el último elemento de la lista y se establece el nuevo elemento actual. Esto se realiza en el procedimiento endElement.
    • El procedimiento characters es idéntico al estudiado en un ejemplo anterior. Simplemente nos aseguramos de verificar que el elemento actual es efectivamente el elemento <error>, una precaución que normalmente no es necesaria aquí. Este tipo de precaución también se tomó en el procedimiento startElement para verificar que se trataba de un elemento <simulation>.

    6.5. Conclusión

    Gracias a su respuesta XML, la aplicación impots se ha vuelto más fácil de gestionar tanto para su diseñador como para los diseñadores de aplicaciones cliente.

    • El diseño de la aplicación de servidor puede ahora confiarse a dos tipos de personas: el desarrollador Java del servlet y el diseñador gráfico que gestionará la apariencia de la respuesta del servidor en los navegadores. Este último solo necesita conocer la estructura de la respuesta XML del servidor para crear las hojas de estilo que la acompañarán. Tenga en cuenta que estas se encuentran en archivos XSL separados, independientes del servlet Java. El diseñador de la interfaz de usuario puede, por lo tanto, trabajar de forma independiente del desarrollador Java.
    • Los diseñadores de aplicaciones cliente, asimismo, solo necesitan conocer la estructura de la respuesta XML del servidor. Cualquier cambio que el diseñador gráfico pueda realizar en las hojas de estilo no tiene ningún impacto en esta respuesta XML, que siempre permanece igual. Esto supone una gran ventaja.
    • ¿Cómo puede el desarrollador actualizar su servlet Java sin que todo deje de funcionar? En primer lugar, siempre que la respuesta XML no sufra cambios, puede organizar el servlet como desee. También puede actualizar la respuesta XML siempre que mantenga los elementos <error> y <simulation> que esperan sus clientes. De este modo, puede añadir nuevas etiquetas a esta respuesta. El desarrollador front-end las tendrá en cuenta en sus hojas de estilo, y los navegadores podrán recibir las nuevas versiones de la respuesta. Los clientes programáticos, sin embargo, seguirán funcionando con el modelo antiguo, ya que las nuevas etiquetas simplemente se ignoran. Para que esto funcione, las etiquetas que se buscan deben identificarse claramente en el análisis XML de la respuesta del servidor. Esto es lo que se hizo en nuestro cliente XML para la aplicación fiscal, donde los procedimientos indicaban específicamente que estábamos procesando las etiquetas <error> y <simulation>. Como resultado, las demás etiquetas se ignoran.
